## 第 0 课：先用人话记住它是什么

DeepSeek Harness（仓库里叫 dsh）不是又一个前端框架。更像「给 AI 用的应用壳」。

三句话就够：

1. 我在网页里打字，程序把话发给 DeepSeek。
2. 模型可以回文字，也可以说「请执行某某工具」；程序真的去跑，再把结果喂回给模型。
3. 仓库里几乎每块功能都是插件。启动时把很多插件拼在一起，就变成完整产品。

`ctx`：插件拿到的工具箱。要登记工具、听事件，都通过它，而不是满仓库去 import 别人内部实现。

以后在这里开发，大概就三类事：

1. 加小插件（给 AI 多一个工具）
2. 改已有功能
3. 改网页（`packages/client/`）

新手从第 1 类开始。Session、profile、seam 这些词当时先放下了。

## 第 3 课：给 AI 加工具 greet

把 `my-plugin.ts` 换成登记一个真正的工具。yml 不用改，还是指向同一个文件。

现在的代码大意：

- `inject = ['tools']`：先等「工具登记处」准备好再加载
- `ctx.tools.register(defineTool({...}))`：挂上工具
- `name` / `description` / `parameters`：给模型看的说明书
- `execute`：真干活，返回 `` Hello, ${args.name}! ``
- `output.render`：把返回值变成模型能读的文本

重启网页后对模型说：

> Use the greet tool to greet Ada.

结果：`Done — the greet tool returned: Hello, Ada!`
说明：插件挂上了，说明书被看见了，`execute` 也跑了。

## 第 4 课：点发送之后发生了什么

最短地图：

```text
我打字发送
  → 程序记下「用户说了这句话」
  → 把说明书（包括 greet）+ 历史打包，发给 DeepSeek
  → 模型说：请调用 greet，参数 name=Ada
  → 程序跑我写的 execute，得到 Hello, Ada!
  → 把这句话再发给模型
  → 模型用正常人话回复我
```

一轮「模型请求 + 它点名的工具」可以叫一次**步骤**；我点一次发送直到模型不再调工具，可以叫一次**回合**。名字先混着用也没关系，地图更重要。

和前端的对照：点提交 ≈ 发送；POST 后端 ≈ 发给 DeepSeek 并附带工具列表；后端 action ≈ 模型选择 greet；业务函数 ≈ `execute`；再请求拿最终文案 ≈ 模型看到工具结果后回复。差别是：可调用列表来自各插件的 `register`，不是我写死的一份 API 文档。

不要混的三份东西：

1. **说明书**（name / description / parameters）—— 模型靠这个决定调不调
2. **execute** —— 模型进不来，只能点名 + 填参数
3. **网页气泡** —— 界面画出来的；刷新能还原，是因为在重放一份只能往后追加的记录（以后会叫 Session 日志），不是 React 自己偷偷存的那份

`scratch-plugin` 只插入了「登记处多一个 greet」。循环、网页、存档都是仓库里别的插件做的。口诀：**先加工具，不要先改引擎。**

### 第 4 课作业（已做）

   后来补了一句：yml 路径错、忘了 `--patch`、忘了 `inject = ['tools']`，同样会「从不调用」。没调用时先问插件有没有挂上，再问说明书清不清楚。

## 第 5 课：在仓库里找该改的文件

不是一个大 `src/`，而是 `packages/` 里很多小包，每个干一件事。打开文件前先问：改的是模型能力、网页，还是对话怎么存？

| 路径 | 是什么 | 我要不要乱进 |
|---|---|---|
| `scratch-plugin/` | 练习场 | 随便改 |
| `packages/` | 产品代码 | 要改功能才进 |
| `docs/` | 说明 | 迷路时查 |
| `apps/` | 启动入口 | 很少改 |
| `vendor/` | 拷进来的 Cordis 等 | 不要改 |

`packages/` 里大概：

- `core/`：循环、工具登记处、系统提示（引擎）
- `fs/`、`shell/`、`web/`：读文件、跑命令、上网
- `client/`：网页
- `llm/`：对接模型

安全区：练习插件；已有工具包里改文案 / 说明书 / execute 小逻辑；以后改 `packages/client/`。
谨慎区：很多包装依赖的接口包；配置、权限、沙箱。
危险区：`packages/core/agent-loop/`；`vendor/`；Session 日志格式/版本。

找文件用搜索，比逛文件夹快。例如 `name: 'todo_write'`，范围 `packages/todo`。

## 第 6 课：练习插件 vs 正规包

会写 greet，就等于会写产品工具的心脏。正规包多的是：让仓库承认它、测它、写进默认启动。

`packages/todo/tool-todo/` 大概有：

```text
src/index.ts      心脏
src/types.ts      类型
tests/            自动检查
package.json      身份证，名字 @deepseek-ai/dsh-tool-todo
README.md
tsconfig.json
```

### 第 6 课作业：我找的 vs 老师纠正的

我找到了 `packages/bundle/base/package.json` 第 108 行：

```text
"@deepseek-ai/dsh-tool-todo": "workspace:^"
```

当时理解：配一个工作区依赖。greet 之所以要 `--patch`，是因为没写进这份 package.json。

**纠正：只对了一半。**

- `package.json`：npm 购物清单，允许引用这个包。`workspace:^` = 用本仓库里的那份。
- **真正启动时挂上插件的是** `packages/bundle/base/cordis.patch.yml` 大约 401–404 行：

```yaml
- id: tool-todo
  name: '@deepseek-ai/dsh-tool-todo'
  config:
    allowParallelInProgress: true
```

这和我的 `scratch-plugin/cordis.yml` 是同一类东西：一边是 `id: hello` + 磁盘绝对路径 + 启动时 `--patch`；一边是 `id: tool-todo` + npm 包名 + 写进 base，每次启动都有。

只有依赖、没有挂载，等于买了包也不会加载。greet 需要 `--patch`，是因为 **yml 清单里没有那一行**，不是因为没写进 package.json。两份都要：能引用 + 写进启动清单。

不要把 greet 写进产品的 `cordis.patch.yml`，那会变成所有人默认都有的玩具。

## 第 7 课：接到「加功能」怎么动手

顺序：

1. 给模型用的，还是给人看的？模型能点名 → 工具；只是网页 → `packages/client/`；都要 → 先工具再界面。
2. 先在 `scratch-plugin` + `--patch` 验证。错了删练习文件就行。
3. 只有「希望别人启动也自带」才进 `packages/`（正规包、测试、依赖 + 挂载两份清单）。
4. 正规包改行为，优先跑这个包的 `tests/`，不要默认跑全仓库。练习场用网页 + 让模型调用。

```text
新想法
  → 练习插件做出来
  → 网页里真的能调
  → 要成为默认功能？
        否 → 停在 --patch
        是 → 再搬进 packages/
```

### 第 7 课作业（已做，对过）

1. `package.json`：npm 购物清单，允许引用这个包（不是「负责本地构建」）。`cordis.patch.yml`：启动时真正挂上插件。
2. 自己开发用的 greet 类工具 **不改** `packages/bundle/base`。继续 `scratch-plugin/` + `--patch`。改 base 等于所有人默认都有。
3. 测试大概在查：会不会登记、参数错了会不会拒、清单怎么写入/覆盖、配置、卸掉后工具会不会消失、界面和回放是否一致。（不是只查「界面标题」那一条。）

网页也是 `packages/client/` 里很多插件。和聊天最相关的三块：

| 屏幕上 | 目录 |
|---|---|
| 底部输入框、发送 | `packages/client/ui-conversation` |

### 第 8 课 C：greet 可配置（已完成）

已做：`my-plugin.ts` 加 `Config`（interface 类型 + Schema 值），`apply(ctx, config)`，execute 用 `config.greeting`；`cordis.yml` 加 `config.greeting`；网页验证返回 `Hi there, Ada!`。

要点：两个同名 `Config` 分工不同——`interface` 是类型（编译后消失，给编辑器看），`const Config = Schema.object(...)` 是值（运行时校验，给 Cordis 看）。**校验靠 schema，不靠类型。** 配置错误会「响亮失败」（插件加载时拒绝）。

### framework 第 1 篇：插件与生命周期（已讲完，作业已对）

一个插件的五个阶段：`PENDING（等依赖）→ LOADING（跑 apply）→ ACTIVE（在跑）→ UNLOADING → DISPOSED`，apply 报错落到 `FAILED`。

- `inject = ['tools']` = 先停在 PENDING 等 tools 就绪（依赖驱动的加载）。
- **自动清理**：通过 `ctx` 登记的工具 / 事件 / effect，插件卸载时自动撤销。第 8 课 B 里 `fiber.dispose()` 后 `todo_write` 自动消失，就因为 register 那一下记好了「归属」，卸载时算总账回收。
- 框架不认识的资源（定时器、网络连接）用 `ctx.effect(() => { ...; return 清理函数 })` 把清理函数交给框架。
- 顺带记住：`ctx.plugin()` 挂子插件；HMR = 杀旧插件 → 清注册 → 加载新代码 → 跑新 apply。

可选手动实验做了：在 `my-plugin.ts` 加 `ctx.effect` 定时器 heartbeat，看 `greet 插件加载` 日志。
